# 显示器控制与交付缺口补全设计

日期：2026-11-07。状态：待用户批准实施。本文件是设计，不是已实现或测试通过的证明。

## 目标与边界

先补齐当前计划内功能和交付缺口，再交 Windows、Mac 实机验收。两台电脑分别通过 HDMI、DP 连接同两块屏，每台都能从当前未选中的视频连接请求切回；复用现有 USB 插拔规则实现自动切换。用户已验证旧 Windows 脚本能控制当前链路，Windows 接受登录后启动。本轮不新增跨主机网络遥控、登录前系统服务或通用安装器。

用户文章中，两块屏的控制方式不同：另一屏使用标准 VCP（显示器控制编码）`0x60`，输入值为 `15/17`；LG 使用 AMD ADL（显卡驱动接口）发送原始 I²C 命令，源地址 `0x50`、私有编码 `0xF4`，示例值 `0xD0/0x91`。这些是配置依据，不能直接把历史设备序号和端口映射写入当前真实配置。

项目已有稳定身份绑定、USB 事件与规则、标准输入控制、五秒预览和登录启动公共接口，应优先复用。现 Windows 后端拒绝 `ProtocolLGInputAlt`（LG 替代输入协议），登录启动也未实现；Linux 随包工具尚未形成真实载荷。已有 Actions 手动构建流程，缺少上传与发布。历史“23/24 完成”不代表这些路径已通过当前实机验收。

## 方案比较与选择

| 方案 | 收益 | 代价与限制 |
| --- | --- | --- |
| 推荐：Windows 原生 AMD 适配，Mac 复用 m1ddc | 沿用现有架构、协议枚举和身份绑定；不默认增加常驻应用 | 需实现并验证 ADL 绑定、目标对应和异常处理；硬件适用范围仍受驱动与连接限制 |
| 调用 amdddc-windows、BetterDisplay 等外部程序 | 复用工具已有控制路径 | 增加安装、进程运行、版本与许可前提；仍不能保证任意扩展坞可用 |

按现有项目架构和用户要求的双端工具目标，推荐第一种。BetterDisplay 仅作为未来可选适配方向，不默认安装、购买或常驻。若实施发现必须新增依赖、改变既有配置含义或扩大显卡范围，应先说明证据和影响。

## 需求与实现范围

### R1：双端独立控制与规则复用

继续走“USB 事件→现有规则匹配→稳定显示器身份→每屏协议与目标输入→逐屏结果”。复用已有 VID/PID、序列号与路径匹配；身份不唯一时拒绝猜测，不照抄文章中的显示器编号。热拔插后重新定位有效目标；多屏部分失败分别报告，沿用已有保护。

### R2：Windows 登录启动

扩展 `internal/loginstart/` 的 Windows 实现，复用 `Manager`、现有 Service/Desktop 目标和桌面后台接口。使用当前用户的 HKCU Run 登录项启动后台及所选桌面目标，保留现有命令参数和启停语义。

公共初始化当前默认调用 `os.Getuid()` 并拒绝负 UID。Windows 中该函数并非编译缺失，而是不提供有效的 Unix 用户编号；应改用适合 Windows 的用户身份、配置目录和安全校验，不能填入虚假 UID 绕过权限判断。登录项只管理本应用自己的值；路径引用、参数转义和删除必须精确，不影响其他登录项。

### R3：Windows LG 特殊协议

在 `internal/backend/windows/` 内为已有 LG 协议增加 ADL 原始 I²C 通路。当前项目没有 ADL 绑定；可复用的是现有系统 DLL 加载模式和已引入的通用能力，不代表已具备 AMD 调用实现。协议使用固定的 `0x50 + 0xF4` 语义，不增加任意原始命令入口；输入值仍来自每屏明确配置。

实施前先确认 AMD 公开接口资料、SDK 与驱动 DLL 的来源和许可、构建要求、函数及结构体调用约定、显示器与 ADL 输出的映射方式。优先只加载用户已安装的受支持 AMD 驱动，不默认随包分发 SDK 或驱动 DLL。上述前提无法确认时，该分项保留受阻状态并报告证据，不得宣称原生适配已完成。

需核验 DLL、函数、结构体、调用约定和资源生命周期，并建立现有显示器身份与 ADL 物理输出的可信对应。存在歧义、驱动接口缺失或目标失效时明确失败；禁止退回另一个显示器或自动扫地址。该路径首先覆盖有相应能力的 AMD 驱动，不据此声称 Intel、NVIDIA、Qualcomm 或全部 AMD 输出均受支持。标准 `0x60` 路径继续复用。

### R4：Mac LG 协议与工具版本

扩展或核实 `internal/backend/darwin/` 的既有适配，按 UUID 选择显示器，标准协议使用 `input`，LG 协议使用 `input-alt`。复用 m1ddc，不从零实现 MacDCP。

已核实上游提交 `7339ceebb03f691b1eaeb8471dca301d215d19c8` 支持替代源地址与私有编码，许可为 MIT。实现前应核对项目实际随包版本与能力，分发保留版权和许可声明。m1ddc 使用 `atoi` 解析参数，因此应先验证配置并转为十进制字符串：`0xD0` 应传 `208`，`0x91` 应传 `145`，不能直接透传十六进制文本。用户历史 M4 Pro 失败记录仍是实机验收依据，不能凭新版源码认定已经解决。

### R5：能力判断、读回与安全预览

能力串可能不准确；LG 明确协议不能仅因未声明标准 `0x60` 被预先否定。对标准路径复用已有读取与诊断能力，证据不足时表达未知，不自动试写地址、协议或输入值。

LG 私有命令可能无法可靠读回。必须区分“命令提交成功”与“已读回验证”，不伪造画面成功。五秒预览仍要求可靠读取原输入、判断外部切换并验证恢复；缺少这些能力时明确预览不可用，普通切换仅按明确协议配置提交。不得为了让预览看似可用而盲目回写覆盖其他操作。

### R6：Linux 实际载荷与许可闭包

按既有 `docs/development/linux-bundled-tools.md` 配方补齐 amd64、arm64 的 ddcutil、busctl、udevadm、所需库、源码来源和许可产物。沿用已记录的 ddcutil 3.0.2、systemd 258 与随包执行策略，不自动升级或改装宿主系统。

验证产物架构、依赖闭包、来源校验和许可完整性，并注明实际支持的运行环境。不能把单一环境生成的二进制称为所有 Linux 发行版通用；缺少某架构产物时保留未完成状态。

### R7：可下载 Windows 候选版与发布

在 `.github/workflows/build.yml` 现有流程上增加适用目标的 Windows 原生测试、桌面构建及配套核心包装，提供 GUI、后台、CLI、所需资源、许可和 SHA256 校验文件；复用现有构建与包装脚本。按现有目标矩阵核对每个产物，不能以交叉编译代替原生测试，也不能仅修改支持表来关闭失败目标。

增加 Actions 制品上传，以及由明确标签或手动条件触发的版本发布入口。当前已确认 origin 目标为 `github.com/orzlees/display-kvm`；本机无 gh CLI，但并不等于其他发布入口不可用。实际推送、运行与发布在实现和验证后按已授权范围进行，并核对真实下载结果；本稿不表示已发布。

沿用现有候选版双进程边界，明确后台与桌面的启动顺序，以及 Windows 版本、WebView2 和文件系统前提。不额外承诺本轮开发通用安装器。若原计划要求的交付方式无法满足，应在计划中保留缺口。

### R8：配置、文档与任务状态

通过现有配置/界面绑定实际设备，提供文章数值的示例解释；不默认写入 VID/PID `1507/1552` 或历史端口映射。同步当前功能限制、Windows 使用说明与陈旧的文档入口，避免“只有规划”“只差测试”等互相矛盾的描述。

按既有任务工作流记录新增补全与验证结果；任务 24 的真实 DDC、USB、登录、休眠及多环境验收尚未通过时，不归档为全部完成。不新建与本任务无关的状态文件或检查点。

## 依赖、验证与完成标准

先确认身份和协议语义，再分别实施 Windows 登录启动、双端 LG 适配与交付流程；共享模型变更由单一写入者负责。只增加必要函数和模块，复用既有接口、错误与状态表达，保留有效注释，不处理其他任务改动。需要新的界面判断时交由 UI 专家处理。

每个实现范围完成针对性测试；独立验证者检查真实变更、配置兼容与原始需求。合并各范围后按影响执行一次必要的核心/桌面回归，Windows runner 执行能脱离真实屏幕的原生测试，另核对候选包结构、架构、校验和与 Linux 依赖许可闭包。记录准确命令、退出码和证据位置；编译成功与测试执行成功分别记录。

实机阶段逐屏验收两台主机从非当前输入切回、USB 插拔规则、登录启动、休眠恢复、热拔插、身份歧义和部分失败。源码核验与模拟测试不能替代这些证据。最终逐项标为已验证、部分完成、未完成或受阻，说明残留；软件补全与实机验收分开收口。
