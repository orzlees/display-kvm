# 开源文档与本地规划的边界建议

状态：草案，待评审。开源项目需要少量清晰、持续维护的文档，不要求公开全部开发过程。本轮只是创建 `docs/` 规划草案，没有选定许可证，也没有改变仓库发布或忽略规则。

## 建议公开维护的内容

- 精简 README：项目用途、限制、安装入口和最短使用路径。
- LICENSE：仅使用本项目明确选定并获批准的许可证；不能把 Fyne 的 BSD 许可证当作本项目许可证。
- 安装和使用、系统权限、配置、事件及 CLI 参考：与实际实现契约保持一致。
- 硬件兼容表和故障排查：区分已实测、未验证、不支持及具体环境，不能用博客或假设补实测。
- 贡献和开发说明，以及有长期维护价值的关键架构设计。

当前草案评审稳定后可选择公开；尚未实现的行为必须保持建议或规划表述，不能写成安装承诺。

## 建议按需保留在本地的内容

聊天原文、AI 派发记录和内部会话信息、临时待办及细碎流水，不应默认进入公共发布资料。密钥、令牌、密码和个人机器配置不得公开；原博客个人硬件编号也不能复制成通用默认值。

`docs/任务计划/` 和 `docs/待办事项/` 用于本系列实施调度、授权与证据追踪，不是发布所必需。它们可留本地，或在去除内部信息后转为 issue。当前文件中含内部角色记录，公开前应审查。是否忽略这些目录属于未来单独选择，本轮不自动调整 `.gitignore`。

稳定公共文档回答“产品如何使用、为什么这样设计”；内部任务文件回答“谁在什么授权范围内做哪项任务、证据在哪里”。两者用途不同，内部流程不应混入产品界面。
